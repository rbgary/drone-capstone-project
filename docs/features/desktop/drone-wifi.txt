--------------------------------------------------------------------------------
1. WHAT IT IS
--------------------------------------------------------------------------------
A small app of ours built into the drone's own firmware: Bitcraze's
crazyflie-firmware 2025.12.1 plus firmware/drone-wifi, built by build.sh into
cf2.bin, which Set up installs as "main". It was written (2026-09) to hand the
AI deck's ESP32 the operator's Wi-Fi network over the radio, so the camera
streamed on the laptop's own network.

There is no camera now (../architecture.txt, DECISIONS). What the app still
does that matters is one read-only parameter, cwsetup.fw — its version. A
drone that reports it runs our firmware; one that does not, or reports an
older one, gets main installed. The other two parameters, cwsetup.deck and
cwsetup.deckid, recorded the AI deck's software and serial; nothing reads
them now, and a drone may keep them, harmlessly.

--------------------------------------------------------------------------------
3. DECISIONS
--------------------------------------------------------------------------------
• OPTION A — KEEP drone_wifi EXACTLY AS IT IS (2026-11-15, chosen by the team
  to keep risk lowest). Three ways were weighed for "is main installed?" once
  the camera went:
    A  keep drone_wifi unchanged; Set up keeps reading cwsetup.fw
    B  trim drone_wifi to the marker alone, rebuild, reflash every drone
    C  ship Bitcraze's own cf2.bin; read main's version from the drone
  A was chosen: no drone is reflashed, and a NEW drone gets the very image
  already flown (flight-log.txt: v4 "as found", later "flashed back"). The
  flight code is stock 2025.12.1 either way — drone_wifi never touched
  flight; its loop blocks on appchannelReceiveDataPacket(...,
  APPCHANNEL_WAIT_FOREVER) and acts only on a packet from the laptop, which
  the agent no longer sends. B was rejected: the most risk (a new image to
  flash and fly) for the least gain (still a custom build).
  THE COST OF A is upkeep, not risk: a custom firmware build (build.sh, the
  ARM toolchain download, the wire test) kept for one parameter, and dead
  Wi-Fi code on every drone.

• OPTION C — THE CLEANUP, WHEN THE TEAM WANTS TO DROP THE CUSTOM BUILD. Not
  done. Nothing in A blocks it. The steps:
    1. ON THE DRONE FIRST: read firmware.revision0 (and firmware.modified) on
       the lab drone running drone_wifi v4. The record says 0x252b4134
       (flight-status.txt, "Firmware"), the same value build.sh's comment
       gives for unmodified 2025.12.1 — expected, since the app is built out
       of Bitcraze's tree. CONFIRM IT; if the two differ, both values must
       count as installed in step 3.
    2. Replace firmware_bundle/cf2.bin with cf2.bin from Bitcraze's
       crazyflie-release 2025.12.1 firmware-cf2-2025.12.1.zip — the zip whose
       lighthouse.bin the bundle already carries (its sha256 is in
       manifest.json). Record the new file's sha256 and source there.
    3. drone_setup.py: read firmware.revision0 in _read_facts; main is
       "installed" when it equals 2025.12.1's revision, "needed" otherwise.
       Drop fw_version / cwsetup.fw and the manifest's "drone_wifi" key.
    4. Delete firmware/drone-wifi/ and this doc's subject with it; update
       commands.txt (FIRMWARE), setup.txt (THE BUNDLE), CLAUDE.md's Layout
       row for firmware/, and the router.
    5. LAB: flash the stock cf2.bin on a drone through Set up, then the
       ladder (flight-log.txt) — hover first. Existing drones need no
       reflash: on the same revision they read as installed and keep
       drone_wifi, harmlessly, until the next time main is written.
  What C buys: no custom firmware to build or maintain. What it risks: a new
  drone gets an image this project never flashed itself (Bitcraze's own
  release, same flight code), until step 5 proves it.

--------------------------------------------------------------------------------
4. INVARIANTS
--------------------------------------------------------------------------------
• MAIN MUST BE crazyflie-firmware 2025.12.1. build.sh pins FW_TAG: building
  from another release changes flight behaviour this project has tuned
  against, not just the app. Options A and C both keep it.
• A NEW cf2.bin MEANS A NEW sha256 AND A HIGHER "drone_wifi" in manifest.json.
  Set up refuses a file whose sha256 does not match (verified_file), and only
  a higher version makes drones that have the old one update.
• THE APP MUST STAY IDLE UNLESS ASKED. It runs beside the flight code on the
  STM32; while nothing sends to it, it does nothing. Do not add work to it
  that runs on its own.
