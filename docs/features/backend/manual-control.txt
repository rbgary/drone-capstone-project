MANUAL CONTROL — assisted flying from held keys
===============================================

NO LONGER LOCKED (2026-11-04, the team). From 2026-09-30 these files were
locked to Samuel, after a day of well-meant changes that each lost the drone
in the lab; the lock was a fingerprint test, a CI workflow, CODEOWNERS and a
CLAUDE.md rule. Samuel left the team and the team removed all four: anyone on
it may change manual flight. What decides how the keys fly: flight/manual.py,
flight/keyframe.py, flight/tuning.py, desktop/src/lib/keys.ts and arrows.ts,
pages/control/ArrowFrame.tsx and App.tsx's keyboard handler. A change to them
is worth re-flying the ladder in ../../flight-log.txt before relying on it.


HOW TO FLY IT (what the operator does)

  Start           the props idle on the floor. Nothing lifts yet.
  W / S           up / down. Hold W to take off. Let go: it holds that height.
  A / D           turn the nose left / right, on the spot. It does NOT change
                  which way the arrows go.
  ↑ ↓ ← →         move. ↑ is the way the NOSE POINTED WHEN IT TOOK OFF — set
                  the drone down facing away from you and ↑ is away from you,
                  ↓ back towards you, ← and → to your left and right. That
                  stays true however much you turn it with A / D.
  SHIFT (hold)    reverses the arrows while you hold it: ↑ comes back, ← goes
                  right. For when the drone faces you. Let go and they are
                  normal again. W / S and A / D are never reversed.
  L               land.
  Emergency stop  hold the button for a second: the motors stop.

  Hold an arrow as long as you need: it keeps pushing for as long as it is
  held, and the drone levels when you let go. With no base stations it has no
  position to hold, so it coasts a little after you let go — tap the opposite
  arrow to stop it. Every flight starts the same way; nothing carries over.

  Keys with no base stations: a 2.5° lean (half the old 5°), built at 8°/s.
  With base stations (position hold): the arrows move it at 0.12 m/s.


WHAT IT IS

Manual mode does not send raw thrust. The window reports WHICH KEYS ARE HELD
about ten times a second; the agent runs a 50 Hz loop that turns that intent
into a height-holding setpoint. Let go of everything and the drone holds where
it is — it does not sink, and with base stations it does not wander off. Each
key moves ONE coordinate of a commanded point; the rest stay locked.

Pressing Start does not take off. It idles the propellers on the ground at
IDLE_THRUST (11000, just above cflib's "10001 = next to no power") so the
operator can see the drone is live. It leaves the ground only while W is held —
or when HOLD AT is asked for.


HOLD AT — RISE TO A HEIGHT WITHOUT HOLDING W

`hold_at(height)` is one press instead of a held finger, and it exists because
Auto cannot do this job: a preset program needs a position estimate and is
refused without one (flight-safety.txt), so on the barometer — the state this
drone is usually in — there was no way to simply go up and hover.

IT ADDS NO CONTROL LAW. It sets a GOAL that the existing height glide drives
towards at the same eased CLIMB_RATE_M_S the W key produces, stopping at the
same ceiling. The drone is flown by exactly the code that already flew it; only
what asks for the climb is new. The guards, the heartbeat dead-man, the leash
and Land are untouched.

IT IS A GOAL, NOT A JUMP. Writing the target directly would step the commanded
height, and the leash and the firmware's controller would answer a step with
everything they have — which is the whole reason the glide exists.

IT SLOWS DOWN BEFORE ARRIVING. Asking for full climb speed up to the last
centimetre coasts the stopping distance past the goal: v^2/2a = 0.15^2/0.6 =
3.7 cm, measured as a 2.6 cm overshoot before the approach profile was added.
The request is capped at sqrt(2 * CLIMB_ACCEL_M_S2 * error), the same shape the
leash uses, so it arrives AT the goal rather than near it.

THE KEYS ALWAYS WIN, and they win by CANCELLING the goal, not by out-voting it.
One place decides (`_height_velocity_locked`): the first version cancelled
inside the goal's own branch, so holding S took the other branch, cancelled
nothing, and the goal resumed the moment the key was released — the drone
climbed back to a height the operator had just flown away from. A test pins
that. Land, an emergency stop and re-arming all clear it too.

UNASSISTED — BAROMETER HEIGHT HOLD (no base stations)

The agent switches the drone to the complementary estimator
(stabilizer.estimator = 1), whose height comes from the BAROMETER, waits 1.5 s,
and reads the floor from it. Flight then uses send_zdistance_setpoint(roll,
pitch, yawrate, z): W/S move a height target at 0.15 m/s up to 0.80 m, letting go
holds it, arrows tilt up to 5 degrees, A/D yaw. Land lowers the target at
0.25 m/s, settles 0.6 s at the floor, then stops — a descent, never a drop. The
Kalman estimator is restored when the flight ends.

EXPERIMENTAL. A barometer height indoors wanders by tens of centimetres and prop
wash disturbs it; the drone also has no position hold, so it drifts. Base
stations remain the real fix — no gain and no agent-side "brake" can hold a
position nothing measures, so none was added (2026-09-30).

PITCH_SIGN (-1) IS RIGHT — verified 2026-09-30, closing the "check it in the
lab" this line used to carry, which also said the two packets disagree on the
sign. The firmware source says they do not: zDistanceDecoder and the rpyt
decoder both pass pitch through unchanged, and controller_pid compares it with
state->attitude.pitch as it stands. sensfusion6 sets that pitch to asin(gx),
with g the world's up in the drone's frame, so nose DOWN reads NEGATIVE: the
up arrow's -5 deg is nose down, which is forward. The lab traces agree (up
arrow: stabilizer.pitch -2 to -4; right: roll +2 to +4, right side down).
"The arrows go the wrong way" unassisted is the frame, not the sign: with no
position nothing knows where the operator stands, so up is the way the nose
faced at takeoff (keyframe.py) — set it down facing away from you.

Replaced (2026-09-16): a raw-throttle law. Its slow ramp through liftoff let the
drone skid on a leg and tumble, and letting go of W held nothing.


THE COMMANDED POINT (assisted only)

The arrows used to send a SPEED: hold one, get 0.20 m/s. A speed says how fast
and never says where, so nothing in the system knew where the drone was meant
to be, and sideways slip during a forward move was invisible to it. Releasing
every key sent a speed of zero, which asks the drone to STOP — not to STAY.

The agent now keeps ONE COMMANDED POINT — x, y, height, heading — and sends it
absolutely every tick, moving or still, with send_position_setpoint(x, y, z,
yaw). Each held key advances one coordinate of that point at its own eased
rate, for exactly as long as it is held:

  Up / Down arrow   away / back       0.20 m/s — from you, or the room's
                                      forward; NEVER along the nose (below)
  Left / Right      round / sideways  0.20 m/s — round you, or the room's
                                      left and right
  W / S             height            0.15 m/s
  A / D             heading           30 deg/s

The coordinates no key is asking for are NEVER WRITTEN TO, so they stay locked
by construction rather than by a routine watching for deviation. That is why W
climbs straight up instead of sliding, and why a forward press travels forward
and nothing else. Let go and the point stops advancing — it is already the
spot to hold, with no capture step and no gap.

Auto-correction is therefore not a mode that switches on. The point is the
only thing the drone is ever told, and the firmware's position controller
closes on it at 100 Hz — where anything agent-side is capped at the radio's
10 Hz. There is deliberately NO extra push past a threshold: an absolute
position is already the strongest correction this link can send, and a
deadband that ignores small error then snaps at it is what lurches.

This is PX4's Position mode and ArduPilot's Loiter, which integrate stick
input into a position setpoint for the same reason. The leash is ArduPilot's
term too.

WHY A SPEED COULD NEVER HAVE WORKED. A quadrotor is underactuated: it only
accelerates along its own thrust axis, so it moves sideways by TILTING, and
any attitude error IS a horizontal acceleration error. One degree of unnoticed
tilt is g*sin(1 deg) = 0.17 m/s^2 — 34 cm of drift in two seconds. A velocity
command leaves that error to integrate into position with nothing observing
position. Only closing the loop on position removes it.

MULTIPLE KEYS. Each axis reads only its own opposite pair, so the axes compose
without interfering. Up+Right climbs while sliding right; Forward+Left travels
diagonally. An opposite pair held together cancels to zero, that coordinate is
not advanced, and it stays locked and ACTIVELY HELD — Up and Down together
really does mean "stay exactly here". Cancelling is a smooth stop, not a
freeze: the rate eases out, so the point runs on a few centimetres and stops
somewhere definite.

THE LEASH. Holding a key advances the point whether or not the drone keeps up.
If something holds the drone back — wind, a snagged leg, a sagging battery —
an unleashed point runs on and builds an error the drone answers with
everything it has the moment it comes free. The point is never allowed more
than LEASH_M (0.30 m) from where the drone actually is, so the worst lurch
possible is a 30 cm one, releasing a key always settles within 30 cm, and the
arrows cannot command more than the drone can really fly.

THE ARROWS FOLLOW YOU, NEVER THE NOSE (2026-09-30, the owner's ask; until
then "forward meant where the nose points"). A drone set down at -116°
(flight-log.txt) or turned with A/D flew "forward" somewhere the operator did
not expect, and after half a turn ↑ came towards them. A quadcopter moves in
any direction without turning, so the heading is now only the nose: A and D
turn it and nothing else. The arrows move the commanded point in the ROOM, in
the frame flight/keyframe.py picks each tick:

  FROM YOU (default)  ↑ away from the operator's spot, ↓ back towards it,
                      ← / → round it — their left and right as they face the
                      drone. Stays right when the drone flies behind them and
                      they turn to face it. ArduPilot's Super Simple mode, DJI's
                      Home Lock; base stations stand in for their GPS.
  ROOM                ↑ is the room's +x — the direction `dronedeck geometry`
                      asked the operator to face the drone along ("the
                      direction you want to call forward").

and falls back, said on screen, when it must:

  near you   within NEAR_OPERATOR_M (0.50 m) of the spot "away" has no clear
             direction: the room's directions, until FAR_OPERATOR_M (0.60 m)
             out again — hysteresis, so a drone at the edge does not flicker.
  takeoff    no position (no base stations, or not reported yet): ↑ is the
             way the nose pointed at liftoff, turned into the drone's frame
             by its heading now (stabilizer.yaw, reported with or without base
             stations). ArduPilot's Simple mode, DJI's Course Lock. Unassisted
             flight is always this: its tilt is rotated by (forward − heading).
  nose       not even a heading reported: the old behaviour.

HOLD SHIFT TO REVERSE THE ARROWS (2026-09-30, the owner: "invert control as
long as you hold it"). ↑ is ↓ and ← is → while Shift is down — for a drone
whose nose points back at you — and the instant it comes up they are as they
were. Worked out in the desktop app from the keys held (desktop/src/lib/
keys.ts, tested by scripts/keys.test.mjs — `pnpm test`); the agent only ever
sees the resulting keys. W / S are never reversed (up is up), nor A / D: a turn
looks the same from anywhere — clockwise from above is clockwise — so
reversing them would turn the drone the wrong way. Nothing is saved or turned.

With no position nothing knows where the operator is — no base stations, and a
Crazyflie 2.1 has no compass; the gyro knows only how far it has turned. So ↑
is always the way the nose pointed at takeoff, kept through A/D turns; Shift is
how the operator says "it is facing me now".

It replaced, the same day, a Shift + arrow "correction" that TURNED the arrows
for the rest of the flight (and before it, Nose buttons whose choice was
saved). Both lost the drone in the lab: a saved "At me" flew ↑ backwards before
every takeoff (trace_7ee43c51), and nine presses of Shift+↑ meaning "reverse"
turned the arrows 90° and sent no movement while Shift was held
(trace_eeb1d2ef). Removed at the owner's word, with /controls/nose, /controls/
speed and /controls/nose/correct. Do not bring back anything that changes what
the arrows mean after the operator lets go.

THE ARROWS ARE GENTLE (2026-09-30, the owner: "fly more steadily"). One setting,
no switch — the Slow / Normal buttons were taken out with the Nose buttons.

                 before     now
  lean, no position    5°     2.5°   half the push: g·tan 2.5° = 0.43 m/s²
  lean builds at    12°/s    8°/s    full lean in ~0.3 s
  arrows, with position  0.20 m/s   0.12 m/s  (KEY_MOVE_SPEED_M_S)
  W / S, A / D     unchanged: 0.15 m/s, 30°/s

With no position a lean is an ACCELERATION for as long as it is held and the
drone coasts after — nothing measures its speed, so nothing can hold one; the
lean is the only bound. A HELD ARROW LEANS FOR AS LONG AS IT IS HELD: for one
build a press leaned at most 1 s, and in the lab ↓ held 2-5 s to bring back a
drone drifting away faded to nothing under the key (trace_7b36d994, 32:14:
3.4° -> 0.3°) — "the keys don't work anymore". A test pins a 5 s hold at full
lean and fails on that build. Keys only:
fly_to() (missions) and hold_at() ("Hover at") keep MOVE_SPEED_M_S and
CLIMB_RATE_M_S — tests fail if the keys' numbers leak into a mission.

THE OPERATOR'S SPOT. "I'm here" (desktop) takes the DRONE's position now —
carry it to your feet, or fly it over your head. Without a mark, "away" is
measured from where this flight took off, as ArduPilot's home is where it
armed. The choice and the spot are kept on the laptop (controls.json,
flight/controls_store.py), per Lighthouse setup rather than per room: Manual
has no room selected, and the spot is a point in the base stations' frame.
Settable in the air (POST /controls/frame, /controls/operator); the next tick
uses it. What the arrows mean now reaches the app as the session's
`controls.live`, on change only — the operator direction turns continuously
as the drone circles, and that is not news.

A mission's keys — a held key taking over from fly_to() — follow the same frame.

Unassisted flight never commands a point: without base stations x and y are
dead reckoning. With no position the loop falls back to the velocity law
rather than inventing a coordinate.


THE GLIDE

Nothing the keys command changes in a step. A press used to set the climb speed
instantly and a release stopped it instantly — a jolt at both ends, and the
height controller answered with the motor hammering in the 2026-09-17 traces.
The climb speed, the assisted arrow velocities, the unassisted tilt and the yaw
rate all ease toward what the keys ask at a bounded rate (CLIMB_ACCEL_M_S2 0.30,
MOVE_ACCEL_M_S2 0.40, TILT_RATE_DEG_S 12, YAW_ACCEL_DEG_S2 90). Releasing W
eases to a stop within about 4 cm and then holds exactly. Land eases out of a
climb before easing into the descent, so pressing Land mid-climb is smooth.

See flight-tuning.txt for the firmware-side half of the same fix.


THE NUMBERS

  TICK_HZ             50            setpoints per second
  HEARTBEAT_TIMEOUT_S 0.5           no word from the window -> land
  IDLE_THRUST         11000         props turning, no lift
  CLIMB_RATE_M_S      0.15          W / S and hold-at, gentle by design
  GOAL_REACHED_M      0.01          a held goal is done within a centimetre
  LIFTOFF_HEIGHT_M    0.05          above this counts as flying
  MAX_HEIGHT_M        1.00          ceiling (assisted)
  MAX_UNASSISTED_HEIGHT_M 0.80      ceiling on the barometer
  LAND_RATE_M_S       0.25          barometer descent
  MOVE_SPEED_M_S      0.20          arrows, in the frame keyframe.py picks
  NEAR_OPERATOR_M     0.50          closer to the spot: room directions
  FAR_OPERATOR_M      0.60          ...until this far out again (hysteresis)
  LEASH_M             0.30          how far the point may get ahead of the drone
  DRIFT_NOTICE_M      0.15          off the point and still correcting -> logged

                                    trusted to move the point (flight_guard.py)
  MAX_PLAUSIBLE_SPEED_M_S 2.0       above this a fix is the estimator, not the
                                    drone (shared with safety/flight_guard.py)
  YAW_RATE_DEG_S      30            A / D
  LAND_S              3.0           graceful descent

  states: IDLE -> ARMED -> FLYING -> LANDING -> LANDED / STOPPED

KEYS (all shown on screen, always)

  Up / Down arrow   away from you / back (Room: the room's forward / back)
  Left / Right      round you (Room: the room's left / right)
  W / S             rise / descend, gently
  A / D             turn the nose — and nothing else
  L                 land gracefully
  Emergency stop    hold one second, no key binding


DECISIONS

- The keys move a POINT, not the drone. Velocity control was replaced outright
  rather than corrected on top of: a second controller on the agent's side of a
  10 Hz link fighting the firmware's own at 100 Hz is the arrangement that
  failed its own simulation at +/-0.2 m and was deleted (flight-tuning.txt).
- Held keys change a height TARGET at 0.15 m/s; they do not change thrust. Raw
  thrust has no height hold: releasing the key drops the drone, and holding it
  climbs without limit. The first version did exactly that.
- Releasing every key holds the current height. The earlier code decayed the
  thrust, which read as "the drone is sinking for no reason".
- "Cut motors" was removed as an operator control and replaced with Land.
  Cutting the motors in the air drops the drone; it survives only as the
  hold-to-activate Emergency stop.
- The window never generates a setpoint stream. It can be closed, refreshed or
  frozen; the drone's behaviour must not depend on its frame rate.


INVARIANTS

- Send ONE zero-thrust setpoint before any other. The firmware's rpyt commander
  locks thrust until it sees thrust = 0, then silently holds every later
  setpoint at zero. Missed, it cost a lab session: the app said the props were
  turning and no key moved the drone. arm() sends it; a test pins it for both
  control laws. The lab's hop_test.py and keyboard_fly.py do the same.

- Schedule ticks against a DEADLINE, not a fixed sleep. sleep(1/50) after the
  work measured 38 Hz end to end, not 50; deadline scheduling measured 50.
- The heartbeat is the dead-man switch. Half a second of silence from the window
  lands the drone — that covers a crashed window, a locked laptop and a closed
  lid, all of which leave a drone in the air otherwise.
- Space is blocked on keydown AND keyup. WebKit activates a focused button on
  Space keyup, so blocking keydown alone still leaves a focused dangerous button
  one Space away.
- A window that loses focus never sees keyup, so blur releases every key. The
  drone then holds its height instead of drifting on with a key stuck down.
- The same guards run in manual as in auto (flight-safety.txt). Manual is not a
  bypass; it is a different source of intent.

- NEVER act on a position that moved faster than the drone can fly. A fix that
  jumps further between two ticks than MAX_PLAUSIBLE_SPEED_M_S (2.0 m/s) allows
  is the ESTIMATOR moving, not the drone, and flying to it drives the drone hard
  towards a place it already is. Measured 2026-09-21 with stale base-station
  geometry: the estimate moved 21 cm in one 0.1 s step (2.1 m/s) with the drone
  sitting still on the floor and both stations received 96 % of the time. The
  arrows command 0.20 m/s, so the bound is ten times any real manoeuvre.
  A rejected fix keeps the previous spot; a reading that PERSISTS is believed
  after about 0.1 s, so a drone genuinely carried somewhere is not ignored.

- Command a point only on geometry measured in THIS room. The point is
  exactly as good as the position estimate under it. Stale geometry does not
  fail loudly — the stations simply disagree — and the drone would then be
  flown to a coordinate that is quietly wrong. Run `dronedeck geometry`
  after any station is moved, nudged or re-aimed.

- Read the estimator's OWN confidence, do not infer one. kalman.varPX/varPY
  are the filter's variance in its own position. Above MAX_HOLD_VARIANCE_M2
  (0.01 m², a 10 cm standard deviation) the fix stops being used to seed or
  leash the point, though the flight continues and the guard keeps its own
  looser bound. The same principle as sys.canfly: a guessed threshold refused
  flights the firmware would have allowed, and guessing in the other direction
  would lock a position the estimator does not stand behind.

GOALS — hold_at() AND fly_to() (fly_to since 2026-09-28)

Both set a GOAL the existing motion drives towards, adding no control law:
hold_at(height) for the height; fly_to(x, y, height) for a point in the room
and a height, at the arrow keys' eased speed (MOVE_SPEED_M_S) and acceleration,
on the same leash, capped at the speed the remaining distance can still be
stopped from — so it arrives instead of coasting past. The goal's velocity is
computed in the room's frame — the frame the arrows move the point in too —
and added as it is; the heading never bends it.

fly_to(…, speed_m_s) (2026-10-01, Samuel's ask): a mission's own travel speed, refused unless
0 < speed ≤ MOVE_SPEED_M_S; None keeps MOVE_SPEED_M_S. It is the only thing
that changed in manual.py — nothing the keys do.

  goal_active        True while either goal is still gliding
  operator_override  True once a held key cancelled a goal; hold_at/fly_to
                     clear it

ANY HELD KEY CANCELS EVERY GOAL, at the top of the tick, before anything moves
— one place decides, so no branch can let a goal steer an axis the operator is
steering. fly_to is refused unassisted and on the ground. This is what the
mission controller flies a mission with (../missions/mission-controller.txt).
Verified by test_manual.py TestFlyTo (13 tests, a drone that follows the
point): arrival within 2 cm, never faster than the keys, no overshoot, right
direction at any heading, keys cancel it, the leash holds, the dead-man lands.
