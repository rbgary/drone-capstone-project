--------------------------------------------------------------------------------
1. WHAT IT IS
--------------------------------------------------------------------------------
The team's requirement (2026-11-04): frames upscaled with Real-ESRGAN, with
CLAHE for contrast, because the higher-ups want the detail it shows. It also
draws detail the camera never recorded — the team accepts that for SHOWING a
frame, and nothing reads it as evidence. It is thousands of times slower
than the pipeline's clahe@1, so it runs once a flight's processing is done:
each session's captured frames, a few at a time, never while flying.

3. DECISIONS
--------------------------------------------------------------------------------
• AFTER THE PIPELINE, NOT IN IT. Nothing in the pipeline reads these frames
  (enhance.txt); a session is queued when one of its flights' processing is
  done, or its own — so it follows the DPP switch, and the frames a finding
  rests on are known before it starts.
• ORDER: a finding's frames first, then manual captures, then the rest. A
  session too long to finish still has the frames people will open.
• CHUNKS OF 5, NEVER IN FLIGHT. Each chunk is `dronedeck upscale --session
  <id> --chunk 5`, a child process at lower priority on half the cores. The
  queue asks the session before each one and waits while a flight is in the
  air: portable (no process suspending), and a takeoff waits a few seconds.
• OPENCV'S dnn, NOT ONNX RUNTIME (2026-11-04). The pipeline contract says
  models are "ONNX, run with ONNX Runtime" (handoffs/sprint-1/done/
  dpp-contract.txt, MODEL FILES). The file is ONNX; running it on the OpenCV
  the agent already ships gave output within 1 grey level of ONNX Runtime,
  with no new dependency — the team's rule (2026-11-08): fewer dependencies,
  as long as the results match. Not a speed claim: the two were never timed
  side by side. ONNX Runtime comes back only for a GPU (step 5).
• A LIST OF STEPS. Upscaling is the only step. Moving the image classifier
  to read upscaled frames was raised and NOT decided: the classifier squashes
  frames to 224×224, so upscaling may give it nothing, and findings resting on
  drawn detail is a team decision still open. Measure first (plan step M).

--------------------------------------------------------------------------------
4. INVARIANTS
--------------------------------------------------------------------------------
• frames.csv is read in a pass of its own (frames.captured), skipping a row
  caught half-written: the session may still be recording, and
  camera/recording.py's read_index — for ENDED sessions — raises on one
  (found by test_a_row_caught_half_written_is_left_for_later).
• What is done is upscaled.csv, never memory. A row is written only after its
  image is renamed into place, so a killed chunk redoes one frame and leaves
  nothing half-written.
• A row counts only for the same steps@version; a new version redoes every
  frame. A frame that failed is not tried again at that version.
• The model runs only if its sha256 matches MODELS.json.
• A chunk that makes nothing and leaves frames FAILS the job — it never loops.
• Closed mid-job, a session stays "running" in display.json and resumes when
  the app starts (DRONEDECK_RESUME=0 turns it off, as for processing).
• CPU: ~0.65 s a frame (median 644 ms over 20 real frames, i9-11900H in WSL);
  a 10-minute session's 1 200 captured frames take ~13 minutes.
