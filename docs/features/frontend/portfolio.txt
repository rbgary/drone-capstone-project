PORTFOLIO — projects, the team, and the website admin
=====================================================

WHAT IT IS

The public side of the website: /projects lists the projects, /projects/<slug>
shows one with its write-up and the team who built it beside it, /team shows
everyone, and /team/<slug> is one person's own page — what they are working on,
about them, their hobbies, their photos and their links. Operators edit all of
it at /admin — no code, no deploy.

A DOMAIN PORT of ../doctor-portfolio (projects, BlockNote write-ups, admin CMS).
Same stack, different subject; structure and idiom kept, vocabulary adapted.

A PERSON'S PAGE

/team/<slug>: the project page's layout with people in it. The main column runs
headline, working-on-now, about, hobbies and photos — each section left out
entirely when it is empty, so a half-written page never shows an empty heading.
The sticky right column lists the whole team, each row in that person's own
accent colour with the current one marked, then the projects they worked on
(from project_members) in their category colours.

The three lists — hobbies, links, photos — are jsonb on team_members, not three
more tables: they are only ever read as a whole person, never queried across
people, and the admin saves them in one write. lib/team-profile.ts parses them
on the way out AND on the way in, so a row can only hold what a page can render,
and a link with a javascript: URL is dropped rather than put in an href.


THE PROJECT PAGE SIDEBAR

Sticky like the contents column on the left. The team is a stack of cards —
the first three layered behind each other — and clicking it fans every card out
in a panel floating over the project list (z-40), closed again by the stack,
Escape or a click elsewhere. Keeping the team stacked is what keeps the column
short enough to stay in view. Every project in the list carries its category's
colour (bar, dot and tint), as in the doctor portfolio; colours come from the
--cat-1..8 tokens via lib/categories.ts — known categories fixed, new ones a
stable colour from their name. The colours are never used for text.


WHERE EACH FIELD IS SEEN

Audited against every visitor component, 2026-09-21. A field an operator can
edit and no visitor can see is a field that will be written once and never
again.

  full_name      /team card · the person's page · beside each project
  role           all three
  bio            beside each project (the stack on a project page) and under
                 the name on their own page. It used to be a FALLBACK for
                 About — `about || bio` — so a bio written next to a filled-in
                 About appeared nowhere, which is what an operator hit.
  headline       their page, under the name
  location       their page
  about          their page, the long section
  current_work   their page, "Working on now"
  hobbies        their page, cards
  photos         their page, the photo wall
  links, email,  their page as pills; website and email also on the /team card
  website_url    and beside a project
  avatar_url     everywhere a person appears

  projects: title, subtitle, summary (the card), category, date_label,
  location, cover_image_url and the write-up are all rendered; summary is
  deliberately the card blurb and does not repeat on the detail page.

  gallery: album title, summary, category, date_label and cover; every item's
  caption and credit, photos and videos alike.

Every page-wording field in lib/site-content.ts is rendered by its page —
checked field by field against each page component, not by eye.


DECISIONS

- Public reads of the portfolio return empty when the tables are missing
  (42P01 / PGRST205) instead of throwing. Vercel ships code before a hand-run
  migration reaches the database; a public page must not blank. The admin reads
  still throw — an operator should see that something is wrong.
- The team is replaced as a set when a project is saved, in the order ticked.
- published_at is stamped on first publish only, so re-publishing an edit does
  not move a project.
- Fonts: Inter (body) and Fraunces (titles), via next/font — the portfolio's
  pairing, shared with the desktop app.
- The seed uses the SECRET key and runs on a developer machine only. The
  projects are starter text drawn from this repo's own docs, to be rewritten in
  /admin. Re-running the seed overwrites the fields it sets.
- team_profiles.py seeds DUMMY profiles so the pages can be reviewed before five
  people have written their own. What it will not invent, because it would
  outlive the seed as a claim about a real person: employers, schools,
  qualifications, locations, email addresses, and links to accounts that might
  belong to a stranger. Roles are a guess, to be swapped in the admin.
- A person's URL is a slug column, not their name at render time. Two people
  called Sam would collide, and a rename would silently move a shared page. The
  admin proposes a slug from the name and then leaves it alone.


INVARIANTS

- BlockNote renders on the client only (next/dynamic, ssr: false), and
  @blocknote/server-util must stay in serverExternalPackages or the build pulls a
  DOM implementation into the server bundle.
- The write-up HTML is injected with dangerouslySetInnerHTML. That is safe only
  because only operators can write projects (RLS) and BlockNote's lossy export
  escapes text. Never let a non-operator write `projects.content`.
- A write that changes no rows is a failure, not a success. Row-level security
  does not raise on UPDATE: a row the policy hides simply does not match, so
  PostgREST answers "no error, no rows" and the editor used to report "Saved ✓"
  over work that never left the browser. Every admin update selects the rows it
  changed and treats an empty result as a refusal (lib/mutations.ts).
- Images are public URLs in a public bucket and cannot be revoked. Never upload
  anything private through the admin — a team member's own photos included.
- Saving a person is refused with "that web address is already taken" on a 23505
  from the unique index, not a generic failure. Two profiles at one URL is the
  one error the admin can actually cause.
- next/image only loads from this project's Supabase storage host
  (next.config.ts remotePatterns). A different bucket host needs adding there.
- Verified 2026-09-16 against the hosted project: anon reads team and published
  projects (200) and cannot write (401) or upload (400); the operator account
  inserts, updates, deletes and uploads (200/204); /projects, /projects/<slug>
  and /team render with no horizontal overflow at 390, 768 and 1280 px.
