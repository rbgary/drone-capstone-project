DATA PIPELINE — the contract every stage builds against
=======================================================

STATUS: VERSION 3 (2026-11-15, branch feat/no-camera; version 2 was
2026-10-09 on dpp/contract-v2, version 1 2026-09-28 on
feat/missions-and-pipeline). The authority is
backend/agent/dronedeck/pipeline/contracts.py; this page describes it. If the
two ever disagree, the CODE wins — tell Samuel so this page is corrected.

WHAT VERSION 3 CHANGED, AND WHY (read this if you built against version 2)
  - THE DRONE CARRIES NO CAMERA (docs/features/architecture.txt, DECISIONS):
    the AI deck is off the airframe. So the pipeline is the SENSORS only —
    clean → classify → interpret, three stages.
  - GONE: Frame, PointData.frames, the enhance stage (Enhancer,
    EnhanceResult, EnhancedFrame, FrameQuality — clahe@1 is deleted),
    ImageVerdict, ViewChange (scene@1 is deleted), ClassifyResult.images and
    .views, Alert.evidence_frames, Finding.evidence_frames / image_support /
    image_note, FrameRecord, FlightResult.frames, FlightContext.mode.
  - classify(data, clean, ctx) and interpret(data, clean, classified, ctx):
    no `enhanced` argument.
  - NO LIVE RUN. A flight is processed once its data has arrived; story 4.9's
    run over the flight so far is removed.
  - Photos taken by hand are classified on their own (story 4.4), not by a
    stage of this pipeline.
  - PIPELINE_VERSION "4"; `dronedeck process --all` re-processes older results.

WHAT VERSION 2 CHANGED, AND WHY (read this if you built against version 1)
  - THE UNIT OF WORK IS THE FLIGHT. Clean, enhance and classify run ONCE over
    the whole flight; every Reading and Frame carries its point_id. Reason:
    an anomaly is a BLOCK of readings that departs from what was expected, and
    a block can span two points or the transit between them — invisible to a
    stage that only ever sees one point (v1 never analysed transit at all).
  - interpret(data, clean, enhanced, classified, ctx) -> InterpretResult: one
    PointResult per inspection point (ctx.points) plus the flight's findings.
  - New types: FrameQuality (on EnhancedFrame), Track, Segment, Event (on
    ClassifyResult), Finding, InterpretResult, FrameRecord (on FlightResult).
  - FlagKind gains "implausible" and "untrusted".
  - PIPELINE_VERSION "2". A v1 result.json still reads on the desktop.

Read this before your own ticket. It is the agreement that lets three people
build three stages separately and have them work together the first time they
are joined.


THE WHOLE SYSTEM, IN ONE PAGE
─────────────────────────────

DroneDeck flies a Crazyflie around a room, stops at pieces of equipment, and
records temperature and pressure at each. (Until v3 it recorded camera frames
too; photos are now taken by hand.)

  1  PLANNING  the operator draws a room (geofence, obstacles) and a mission
               in it: an ordered list of INSPECTION POINTS. (Samuel, built.)
  2  FLYING    the mission controller flies the mission through the manual
               flight system; while the drone HOLDS at a point, every reading
               is stamped with that point's id. (Hannah.)
  3  PROCESSING  THIS PIPELINE: the stamped readings go through clean →
               classify → interpret once the flight has landed, and each
               point gets a verdict. (Samuel, Kevin, Reagan.)

  readings ─▶ clean ─▶ classify ─▶ interpret ─▶ result.json
              Kevin    Reagan      Samuel
              (4.2)    (4.6)       (4.6)

Planning story 4.5: "A single command turns a recorded flight into a result
with a verdict for each inspection point." That command exists:

  dronedeck process --flight <flight id>     a flight on this laptop
  dronedeck process --fixture                the test fixture (source checkout)

THE UNIT OF WORK IS THE FLIGHT (version 2), not one row or one point. The
runner hands every stage the whole flight as one PointData whose point is
"flight" (contracts.WHOLE_FLIGHT), transit included; each reading says which
inspection point it was taken at (point_id, None in transit), and ctx.points
lists the mission's points in order (() with no mission). A stage must still
accept ANY PointData — a single point's readings, or none.


WHERE IT RUNS, AND WHY IT IS BUILT THIS WAY
───────────────────────────────────────────

On the laptop, inside the agent: the laptop has every reading the moment the
drone lands, and needs no network to process them.

Built to move to a cloud worker later without rewriting a stage:

  PORTS AND ADAPTERS   the core has two ports — where a flight comes from
                       (sources.FlightSource) and where a result goes
                       (sinks.ResultSink). LocalFlightSource and
                       LocalResultSink are the laptop's adapters; a cloud
                       worker is two more.
  DEPENDENCY INJECTION compose.py builds the pipeline by handing each stage the
                       implementation to use (the composition root).
  STRATEGY             each stage is an interface (a Protocol); your class is
                       one implementation. Plugging in is a one-line change.

The runner runs in the command's own process (it flies nothing). The agent
starts that command as a PROCESS OF ITS OWN, never a thread beside the 50 Hz
flight loop — CPU work there competes for Python's one interpreter lock, and a
late setpoint drops the drone. That is why every stage must be self-contained.


HOW THE AGENT RUNS THE PIPELINE (built 2026-09-29)
───────────────────────────────────────────────────

Nobody has to type the command any more. The operator has a DPP switch per
session — on by default in Auto, off in Manual — and every flight that began
with it on is processed WHEN IT LANDS (backend/agent/dronedeck/processing.py):

  - the agent starts `dronedeck process --flight <id>` as a CHILD PROCESS,
    at lower priority, after the flight's CSV is closed;
  - ONE FLIGHT AT A TIME; 15 MINUTES for the whole flight, every point and
    every stage — then it is stopped and marked failed. Rule 12's per-point
    targets keep a 20-point mission far inside that;
  - EXIT CODE 0 is success. Anything else is a failure, and the LAST LINE the
    command printed is the reason the operator reads. The runner already
    turns stage failures into results, so a non-zero exit means the whole
    command could not run — say why in words;
  - the result is shown on the desktop: the Fly step's Results panel (Auto)
    and the Data processing panel (Manual), point by point, with each
    PointResult's reasons printed VERBATIM. Write them for an operator.

WHAT A FLIGHT LOOKS LIKE NOW (also 2026-09-29):
  - THE PLAN FLOWN (sessions/<id>/missions/<flight>.json) is the mission AS
    FLOWN: its `home` is where the drone really took off (a flight starts
    wherever the drone is), and points after the operator's END POINT are
    not in it. Only the points in it were flown; read nothing else.
  - A MANUAL flight is one point, "flight", as before — and it is now
    processed whenever the operator turns DPP on in Manual.
  - Heights are above the floor where the drone took off (CLAUDE.md
    invariant 4). The Auto confirmation now tells the operator to take off
    from the floor.

THE TYPES (contracts.py)
────────────────────────

Shared input

  FlightContext        flight_id, session_id, temp_unit ("C" | "F" — the unit
                       of EVERY temperature), ground_z_m, started_at (UTC),
                       workdir (the ONLY place a stage may write), points
                       (the mission's inspection points in order; () with no
                       mission)
  InspectionPoint      id, label, x_m, y_m (absolute Lighthouse metres),
                       z_m (above the floor captured at takeoff)
  Reading              index (unique within the flight), recorded_at (UTC),
                       t_s (seconds since the flight's first row), values:
                       Mapping[str, float | None] — numeric columns by name,
                       point_id (None in transit), text: the row's words
                       (mode, thermal_state, event)
  PointData            point, readings (by index). The whole flight is one,
                       with point "flight".

The names in Reading.values are TelemetryRow's field names
(dronedeck/telemetry/row.py — the authority). The ones that matter:

  raw_temp, corrected_temp           temp_unit    the sensor; after correction
  deviation, thermal_offset,         temp_unit    the correction engine's working
  ambient_est, expected_raw
  roc_per_s                          temp_unit/s
  station_pressure_hpa,              hPa
  sea_level_pressure_hpa
  pressure_altitude_m                m
  battery_v                          V
  x_m, y_m, z_m                      m            z above the floor at takeoff

Stage 1 — clean (story 4.2)            class Cleaner(Protocol)
  clean(data, ctx) -> CleanResult
  CleanResult(readings, flags)         readings: EXACTLY the input, unchanged
                                       usable(index, column) -> bool (provided)
  ReadingFlag(index, column, kind, reason)
                                       column None = the whole row (a gap)
                                       kind: missing | out_of_range | spike |
                                             stuck | gap | implausible (a
                                             change no drone can make) |
                                             untrusted (a position the drone
                                             did not measure)

Stage 2 — classify (story 4.6)         class Classifier(Protocol)
  classify(data, clean, ctx) -> ClassifyResult
  ClassifyResult(sensors, features={}, tracks=(), segments=(), events=())
                                       sensors: one Label for the readings
                                       features: names carry units ("temp_max_c")
                                       tracks: per signal, observed and expected
                                         per reading index, the noise, the model
                                       segments: the blocks found
                                       events: the stretches that depart from
                                         expected — one block, or adjacent
                                         blocks departing the same way (delta,
                                         z, peak, slope, points, mean position
                                         when measured)
  Label(value, p_faulty, model, reason=None)
                                       value: normal | faulty | unknown
                                       "unknown" MUST have a reason (checked
                                       when the Label is built); p_faulty 0..1
                                       model: "<name>@<version>"

Stage 3 — interpret (Samuel)           class Interpreter(Protocol)
  interpret(data, clean, classified, ctx) -> InterpretResult
  InterpretResult(points, findings=())  points: ONE PointResult PER
                                       INSPECTION POINT, in ctx.points order
                                       (just "flight" with no mission)
  PointResult(point_id, verdict, reasons, alerts=())
                                       verdict: normal | anomaly | insufficient_data
  Alert(point_id, severity, reason, evidence_readings)
  Finding(id, signal, severity, title, sentence, start/end index and time,
          unit, observed, expected, delta, z, point_ids, x/y/z_m)
                                       severity: info | warning | critical
                                       the readings are the evidence

The flight's result                    FlightResult, saved as JSON
  flight_id, pipeline_version, stages ({"clean": "name@version", …}),
  created_at, points (one PointResult each), failures (StageFailure: "flight",
  stage, reason), summary (per point: readings, flags; "_transit":
  readings that belonged to no point), session_id, temp_unit, findings,
  flags (every ReadingFlag), tracks, segments


WHAT THE RUNNER DOES WHEN A STAGE GOES WRONG (runner.py)
────────────────────────────────────────────────────────

A stage that fails never takes the flight with it. The failure is recorded and
the flight goes as far as it honestly can:

  clean fails       nothing is analysed: every point insufficient_data.
                    Analysing readings nobody checked is what cleaning exists
                    to prevent.
  classify fails    the sensor label "unknown", with the failure as the reason.
  interpret fails   every point insufficient_data, with the failure as the
                    reason.

A stage that BREAKS THE CONTRACT — a cleaner that edits or drops a reading, an
interpreter that does not give every inspection point one verdict in order —
is treated exactly like one that failed.

Raise StageError("words for the operator") when your stage cannot run at all
(a missing model file). Any other exception is logged with its traceback.


RULES EVERY STAGE FOLLOWS
─────────────────────────

[checked] = test_conformance.py verifies it on every pull request.

 1. SELF-CONTAINED. Output depends only on the input and your model file. No
    network, no Supabase, no other flights. Never import dronedeck.flight,
    .session, .api, .sync or .camera.                                 [checked]
 2. (Retired in v3: one output per frame, in order — there are no frames.)
 3. NEVER CHANGE OR DELETE THE INPUT. Cleaning FLAGS; the next stage skips
    what is flagged.                                                  [checked]
 4. FILES ONLY UNDER ctx.workdir. (No longer checked: no stage writes files
    since enhance went in v3.)
 5. SAME INPUT, SAME OUTPUT. Fix every random seed.                   [checked]
 6. AN EMPTY POINT IS A RESULT, NOT AN EXCEPTION. Stages are checked on the
    whole flight, on each point's own readings, and on an empty point. [checked]
 7. FAIL SMALL, SAY WHY: what cannot be judged gets "unknown" and a reason; a
    stage that cannot run raises StageError. Never swallow an exception silently.
 8. UNITS: metres, seconds, hPa. Temperatures arrive in ctx.temp_unit —
    convert them yourself, and name converted features with their unit.
 9. VERSION HONESTLY: bump `version` whenever your output could change.
10. LOGGING: log = logging.getLogger(__name__). No print.
11. RUNTIME DEPENDENCIES are numpy, Pillow, opencv-python-headless and
    onnxruntime — they go into the desktop installer (OpenCV took the frozen
    agent from 43 to 86 MB, 2026-10-09; it stays for the photo classifier). Anything else, ask Samuel. Training
    in ml/ may use anything.
12. TIME: measure your stage per point on the lab laptop and put it in the PR.
    Targets: clean < 0.2 s; classify < 2 s.


MODEL FILES
───────────

Runtime model files go in dronedeck/pipeline/models/ with an entry in
MODELS.json (a JSON list; empty today):

  {"name": "mobilenetv3-small-faulty", "version": "2026-10-05",
   "file": "mobilenetv3-small-faulty-2026-10-05.onnx", "sha256": "…",
   "source": "trained in ml/image-classifier/ from torchvision
              MobileNet_V3_Small_Weights.IMAGENET1K_V1",
   "license": "BSD-3-Clause (code); ImageNet weights, research use",
   "input": "1x3x224x224 float32, grayscale repeated to 3 channels",
   "output": "1x2 logits [normal, faulty]", "threshold": 0.5}

- ONNX, run with ONNX Runtime. Train in anything, export to ONNX; the same
  file then runs on the laptop and on a future cloud worker.
- NO DOCKER. These are ordinary Python packages in the agent's environment;
  Docker cannot reach USB on macOS anyway (CLAUDE.md invariant 7).
- Committed model files under 20 MB. Datasets never committed — a manifest
  CSV (file, label, angle, session, date) instead.


HOW YOU PLUG IN
───────────────

1. Put your class in your stage's folder: stages/clean/robust.py →
   class RobustCleaner (with `name` and `version`).
2. Add it to the list in tests/pipeline/conformance.py. Every check in
   test_conformance.py now runs against it.
3. Change the one line in compose.py from the stub to your class.
4. Run it: `dronedeck process --fixture` (writes to tests/pipeline/fixtures/
   results/, which git ignores), then on a real flight with --flight. Open
   result.json and read your stage's output.
5. Gates, from backend/agent/: ruff check . && mypy dronedeck && pytest.
   Open the pull request.
